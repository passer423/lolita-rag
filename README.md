# lolita-rag

微博 **Lolita（洛丽塔）社区语料**的检索增强问答（RAG）工具。

采集微博上与 Lolita 相关的博文 → 清洗切分 → 向量化入库 → 混合检索 → 由大模型
**只依据检索到的语料**生成带引用的答案。

> 定位：个人研究/自用。仅供学习检索与 RAG 工程实现，采集结果请勿二次公开发布。

---

## 快速开始

```bash
# 1) 安装依赖（本机已装好可跳过）
pip install -r requirements.txt

# 2) 配置（可选：不配置也能用 mock 语料跑通全流程）
cp .env.example .env        # Windows: copy .env.example .env

# 3) 建索引 —— 默认使用内置 mock 语料，不需要网络和 Cookie
python scripts/build_index.py

# 4) 提问
python scripts/ask.py "带亮片的裙子应该怎么洗？"
python scripts/ask.py --interactive

# 5) 跑评测，得到 Recall@k / MRR / 拒答准确率
python scripts/eval.py
```

想用真实微博数据（**需要 Cookie**，见下方「采集前置条件」）：

```bash
python scripts/crawl.py --keyword Lolita --pages 1 --dry-run   # 先确认解析正常，不写盘
python scripts/crawl.py --keyword Lolita --keyword 洛丽塔 --pages 3
python scripts/build_index.py --source raw          # 增量建索引
```

### 没有 API Key 会怎样

**不会报错。** `LLM_API_KEY` 为空时，答案会自动退化为「原文摘录 + 来源编号」
模式，并在末尾注明未配置模型。这样可以先验证检索链路是否正常，
再决定要不要接模型——出问题时能立刻分清是**检索坏了**还是**生成坏了**。

## 真实语料的两条获取路径

微博的关键词检索接口**必须要登录态**（实测：未登录 `getIndex` 返回 `ok: -100`，
话题页直接 HTTP 432，`s.weibo.com` 是 Sina Visitor System 登录墙）。
公开能拿到的只有热搜词（`weibo.com/ajax/side/hotSearch`），**没有博文正文**，
构不成语料。所以只有下面两条路。

### 路径 A：配置 Cookie（自动采集）

**最可靠的拿 Cookie 方式是从 HAR 抓包里取**——手工从 F12 复制很容易漏字段
（实测漏过 `SSOLoginState` / `_T_WM`，服务端就只认游客身份），而 HAR 里存的是
浏览器发出去的**完整** Cookie 请求头：

```bash
# 浏览器已登录 → F12 → Network → 翻几页 → 右键 → Save all as HAR with content
python scripts/extract_cookie.py --input capture.har --write --verify
```

`--verify` 会只花 1 个请求确认登录态，并告诉你 Cookie 里缺哪些常见字段。
脚本输出**不会显示 Cookie 内容**，只有长度与字段名。

手工复制也可以，但请复制**整个** cookie 头的值：

```bash
python scripts/check_login.py          # 1 个请求验证；失败时会指出缺哪些字段
```

验证通过后：

```bash
python scripts/crawl.py --keyword LOLITA超话 --keyword lo裙 --pages 1 --dry-run   # 先验解析
python scripts/crawl.py --keyword LOLITA超话 --keyword lo裙 --pages 10
python scripts/build_index.py --source raw     # 增量，只编码新增
```

> 换个 HAR 就能同时拿到**语料和 Cookie**——`import_weibo.py` 吃语料、
> `extract_cookie.py` 吃 Cookie，两个脚本读同一个文件。
>
> ⚠️ 但 HAR 里**必须有一条 `m.weibo.cn` 的请求**：`s.weibo.com` 和 `m.weibo.cn`
> 是不同的域，搜索页那份 Cookie 经常缺移动端接口要的字段，直接抽出来会 `login=false`
> （实测缺 `SSOLoginState` / `_T_WM`）。所以在导出 HAR 前，顺手打开一次
> `https://m.weibo.cn/api/config` 就够了；`extract_cookie.py` 会**优先挑**
> `m.weibo.cn` 的那份 Cookie，而这条 JSON 响应不会混进语料。

### 路径 B：手工保存 / HAR 抓包再导入（**不需要交出 Cookie**）

你在浏览器里本来就是登录状态，把浏览器已经拿到的数据存成文件即可。

**推荐：一次 HAR 导出拿到几十页**（比一页一页 Ctrl+S 快一个量级）：

```bash
# 1) 先生成需要访问的搜索链接（内置超话名/领域词表，直接搜「Lolita」容易混进小说电影）
python scripts/search_urls.py --pages 5

# 2) 在浏览器里逐个打开这些链接（可中键批量打开）
#    **再额外打开一次 https://m.weibo.cn/api/config**（只返回一行 JSON，不产生语料）
#    确认加载完成后：F12 → Network → 右键 → Save all as HAR with content

# 3) 一次导入整个抓包；--exclude 用来丢掉营销/交易贴
python scripts/import_weibo.py --input capture.har --dry-run
python scripts/import_weibo.py --input capture.har \
    --exclude "出物,抽奖,转发,上新,图透,预约,尾款,定金"

python scripts/build_index.py --source raw     # 增量，只编码新增
```

> 实测：排除上面那组词后语料 **21 → 11 条**——微博搜索页里约一半是营销/交易贴，
> 它们对问答没价值却会稀释检索结果。建议「知识语料」过滤后入库，
> 原始数据另存留档。

也可以单页保存（`Ctrl+S` 存 `.html`，或 F12 里 Copy response 存 `.json`），
放进同一个目录后一起导入：`python scripts/import_weibo.py --input saved/`。

导入器支持：

| 类型 | 说明 |
|---|---|
| `.har` | 浏览器抓包，**一次包含所有页面**，自动跳过 JS/CSS/图片 |
| `.json` | container 接口响应 / 裸 cards 数组 / 裸博文数组 |
| `.html` | `s.weibo.com` PC 搜索页（Ctrl+S 保存的）、含 `$render_data` 的移动端页面 |
| `.jsonl` | 本项目 `posts.jsonl` 格式 |

**识别不了时不会静默丢弃**，而是把看到的结构打印出来，据此补适配即可。
相邻页的重复内容会在导入时自动去重。

两条路最终都写进同一个 `data/raw/posts.jsonl`，之后的清洗/切分/建索引完全一致。

## 增量更新与断点续爬

这两项是语料开始增长后最先吃紧的能力，因此已经内置。

### 增量更新（默认行为）

```bash
python scripts/build_index.py --source raw     # 只编码新增/变更的片段
python scripts/build_index.py --rebuild        # 需要时全量重建
```

机制：以 `chunk_id`（`post_id#序号`）为键与 `data/processed/chunks.jsonl` 比对，
**只对新增或正文变化的片段**调用模型；博文被改短/删除时，多余的旧片段会被
从向量库里 `delete` 掉，不会留下幽灵内容。

三种情况自动强制全量重建，并在输出的「说明」里写清原因：

1. 没有 `manifest.json`（首次构建）；
2. `EMBEDDING_MODEL` 变了（旧向量维度/语义都不再可比）；
3. 向量库条数与片段数不一致（索引被外部改动过）。

### 断点续爬

```bash
python scripts/crawl.py --keyword Lolita --pages 3   # 中断后重跑同一条命令即可续爬
python scripts/crawl.py --pages 6                    # 关键词从进度文件读取，继续往下采
python scripts/crawl.py --keyword Lolita --pages 3 --restart   # 忽略进度，从头重采
```

机制：`data/raw/crawl_state.json` 记录每个关键词的 `next_page`，**每翻完一页就落一次盘**
（博文 + 进度），因此中断最多只丢一页。页码语义是「下次该采哪页」，所以把
`--pages` 从 3 调到 6 再跑，第 1~2 页不会重复采集。同一页重采是幂等的
（按博文 id 合并进 `posts.jsonl`）。

## 每日自动更新（凌晨定时）

```bash
# 1) 先手动跑一次，确认 Cookie 有效、能采到数据
python scripts/daily_update.py

# 2) 只打印将要做的事（含生成的 XML），不改动系统
python scripts/register_task.py --dry-run

# 3) 注册：每天 02:00 运行
python scripts/register_task.py --time 02:00

# 4) 查看任务状态与最近几次运行
python scripts/register_task.py --status

# 5) 立刻触发一次
python scripts/register_task.py --run-now

# 6) 不再需要时注销
python scripts/register_task.py --unregister
```

> **为什么注册脚本是 Python 而不是 `.ps1`**：本机只有 Windows PowerShell 5.1（没有 `pwsh`），
> 它会按 ANSI 解码**没有 BOM** 的 UTF-8 文件——`.ps1` 里的中文会变成乱码并吞掉引号，
> 直接变成语法错误；而**任何一次编辑都会让文件丢掉 BOM**（实测如此），
> 所以「靠 BOM 保住中文 `.ps1`」并不可靠。改用 Python + `schtasks.exe` 没有这个陷阱。
> `scripts/register_task.ps1` 仍保留，但只是一个**纯 ASCII 的转发壳**，把参数转给
> `register_task.py`。

一次运行做五件事，顺序都是有理由的：

| 步骤 | 作用 | 为什么这样做 |
|---|---|---|
| 单实例锁 | `data/.daily_update.lock` | 上一次没跑完又被触发会让请求频率翻倍、进度账本互相覆盖；陈旧锁（>6 小时）可被接管，避免被强杀后永久卡死 |
| 登录态预检 | 1 个请求查 `/api/config` | **失效即停止**：未登录就不发任何采集请求，不浪费配额 |
| daily 采集 | 重扫前 N 页 | 新内容在搜索结果顶部；与 backfill 的游标互不干扰 |
| 增量建索引 | 只编码新博文 | 没有新增时直接跳过，避免每晚白加载一次模型 |
| 写历史流水 | `data/logs/history.jsonl` | 一行一次运行，可看「每天新增多少条」的趋势 |

退出码（任务计划器可据此告警）：

| 码 | 含义 | 需要你做什么 |
|---|---|---|
| 0 | 成功 | 无 |
| 2 | 配置 / 采集 / 索引错误 | 看 `data/logs/update-*.log` |
| 3 | **Cookie 失效** | 重新复制 Cookie 写入 `.env` 的 `WEIBO_COOKIE` |
| 4 | 已有实例在运行 | 无（本次正常跳过） |

### 关于「自动登录」：本项目不做

**不会**实现用账号密码自动登录微博，也**不会**绕过验证码 / 短信 / Sina Visitor System。
原因有两层：这违反平台条款；而且微博登录几乎必然弹验证码，任何「能自动登录」的实现
本质都是在绕它。

本项目坚持**把「登录」和「使用会话」分开**：

- 登录永远由人在浏览器里完成；
- 程序只复用人工建立的会话（`.env` 里的 `WEIBO_COOKIE`）；
- 会话失效 → 立刻停止 + 记日志 + 退出码 3，**绝不尝试自己「修复」登录态**。

### 运行条件与限制

- 任务在**当前用户身份**下运行，**需要该用户处于登录状态**：锁屏可以，注销 / 关机会不跑；
- 已开启「错过后尽快补跑」（`StartWhenAvailable`），所以笔记本晚上休眠、第二天开机后会自动补上；
- 想做到「注销后也能跑」，需要用带密码的凭据注册（`schtasks /RU /RP`），该步骤需要管理员权限，请自行决定是否采用；
- 每晚请求量 = `DAILY_KEYWORDS 个数 × DAILY_PAGES`，默认 **2 × 2 = 4 个请求**，间隔 2.5 秒。

## 设计要点

### 为什么是混合检索，而不是纯向量

Lolita 圈有大量专有词与黑话：**JSK、OP、柄图、痛lo、KC、茶会**。
稠密向量对这类低频专有词不敏感，而 BM25 恰好擅长精确匹配，所以两路都要。

> ⚠️ 补一句实测后的修正：BM25 的作用**不是「多召回一批向量找不到的片段」**。
> 补上「向量下限对每一路都生效」之后（原因见下文「闸门必须对每一路生效」），
> 关键词路独立送片段进结果需要**命中 ≥2 个不同内容词**才放行。
> 它的主要价值变成**对候选重新排序与提权**：同样的候选池里，「柄图」「冠之礼」
> 这类精确命中能把正确博文顶到前面。这是为了让「能说出语料里没有」成立的代价，
> 权衡写在此处，不做隐藏。

### 融合方式：默认用 weighted，不用 RRF

最初这里用的是 **RRF（Reciprocal Rank Fusion）**，理由是它对两路分数尺度不敏感、
几乎免调参。但实测发现它在**小候选集**下会坏事：

```
查询「带亮片的裙子应该怎么洗？」
  BM25 : 正确博文 9.17 分，另一篇只匹配了「裙子」的拿 1.43 分 —— 差 6.4 倍
  RRF  : 1/61 = 0.01639 与 1/62 = 0.01613 —— 差 1.6%，几乎同分
```

于是「只匹配了一个常见词」的文档被抬进 top-k，用户看到一堆不相关内容。
RRF 的压平特性在大候选池里是优点，在这里是信息损失。

所以默认改成 **`FUSION_MODE=weighted`**：每路先按本查询内的最高分归一化，
再线性加权，保留「好多少」的信息。改完后同一个查询里
第 1 名与第 2 名的分数差从 3% 变成 **17 倍**，噪声被压到不会入选的位置。
`FUSION_MODE=rrf` 仍然保留，便于对比。

### 三道闸门（缺一不可）

稠密检索**永远**会返回「最近的若干条」，哪怕它们毫不相关；BM25 也会被
「裙子」「图片」这类常见词带偏。所以三道闸门都要有：

| 参数 | 作用 | 依据 |
|---|---|---|
| `MIN_VECTOR_SCORE` | 向量相似度**绝对**下限，低于它一律不进结果 | 用 `--scan` 标定。**注意：它现在对每一路都生效**，包括只被 BM25 命中的片段（见下） |
| `MIN_BM25_RATIO` | BM25 **相对**下限（本查询最高分 × 比例），剪掉只匹配常见词的尾巴 | BM25 绝对值随语料规模变化，只能用相对值 |
| 内容词要求 | 查询里若有长度 ≥2 的词，片段必须命中至少一个 | 实测「怎么用 Python 写快速排序？」曾命中缎带手作帖，只因里面有个「用」字 |

#### 闸门必须对**每一路**都生效（真实语料把这里打穿过一次）

最初的实现里，向量下限只管向量路、内容词要求只管 BM25 路，于是**没有任何一路能
独立证明相关性**。语料从 21 条涨到 690 条后，拒答准确率立刻从 1.000 掉到
**0.500**，三个漏网案例各暴露一个侧面：

| 问题 | 漏进来的机制 |
|---|---|
| 红烧肉怎么做才不腻？ | 纯向量噪声：相似度 **0.5049** > 下限，但片段里既没有「红烧肉」也没有「不腻」 |
| 如何用 Docker 部署一个 Node 服务？ | BM25 只命中一个疑问词**「如何」**（df=1，idf 极高），任何文档都可能碰巧有它 |
| 明天北京的天气怎么样？ | BM25 只命中「北京」「明天」这类泛词，相似度仅 0.379 |

两处修法，都写进了测试防止回归：

1. **闸门提升到融合之后统一执行**：任何返回的片段都必须满足「向量 ≥ 下限」且
   「命中 ≥1 个查询内容词」。副作用要说清楚——关键词路不再**引入**新片段，
   只对候选重新排序；但这是「能说出语料里没有」的前提。
2. **疑问词从内容词里剔除**（`QUESTION_WORDS`）：「如何 / 怎么样 / 哪些 / 哪几种」
   长度 ≥2、看起来像内容词，实际是疑问结构的一部分。

> 只按向量下限一刀切会**误拒真答案**：真正相关的「谢安然今天穿的是哪个牌子？」
> 那条博文相似度低于下限，只靠关键词路才找得到。所以留了一个逃生门——
> **命中 ≥2 个独立内容词**即视为关键词证据（`BM25_ONLY_MIN_CONTENT_MATCHES`）。
> 一个词是巧合，两个词才是证据：「北京」算巧合，「安然 + 今天」不算。

> ⚠️ **换 embedding 模型、或语料规模明显变化后，`MIN_VECTOR_SCORE` 必须重新标定。**
> 21 条语料上相关/不相关是 0.44 / 0.38 的干净空隙；690 条时两者已经重叠
> （相关最低 0.4602，语料外最高 0.5049）——**光调阈值已经分不开**，必须靠上面这套
> 组合闸门。这也是 `--scan` 现在要一起看「内容词命中」那一列的原因。

### 检索质量的第二轮修复（用 12 条真实提问体检出来的）

第一轮把指标做到了 1.000，但那只说明**旧评测集太容易**——17 题里 11 题标注的是最早
那批导入博文。于是换了个测法：**拿 12 条真实用户会问的问题直接打检索器，看那 5 条
结果到底是什么东西**。体检结果暴露了三个问题，每个都有具体数字：

| 体检项 | 修复前 | 修复后 |
|---|---|---|
| 返回结果里 20 字以内的废话占比 | **25%**（「就这样幸福的痛lo」这类 15 字贴能拿 1.362 分排第 1） | **2%** |
| `KC 是什么` / `柄图是什么` | **0 条**（系统性拒答） | 5 条 |
| 12 条查询里的拒答数 | 3 条（其中 2 条是误拒） | 1 条（语料确实没有） |

三处根因与修法：

**1. 单术语查询被系统性拒答。** 关键词路的证据门槛是「命中 ≥2 个内容词」，而
`KC 是什么` 的内容词只有 1 个（`什么` 是疑问词），**永远凑不够 2 个**，于是语料里
明明有 5 条在讲 KC 却一条都返回不了。修法：门槛改成「命中的词数 ≥2 **或**把查询的
内容词**全覆盖**」——单词查询下「命中了唯一那个词」本身就是最强的证据。

**2. 指示代词被当成生僻词，常见词又太容易命中。** 内容词闸门只要求「命中至少一个
长度 ≥2 的词」，而 `裙子` df=98/615、`lo` df=163/615——命中它们等于没命中。实测
「藤上春这条裙子多少钱」的 top-5 里有 **4 条只命中了「裙子」**；更糟的是
`这条` df=9 被误判成「生僻词」，反而把无关博文留了下来。修法两条：

* `这条/那种/这些…` 进停用词（**指示代词没有区分度，与出现频率无关**）；
* 新增**生僻词闸门**（`DISTINCTIVE_DF_RATIO`，默认 10%）：查询里存在生僻词时，
  片段必须命中生僻词，**或者具备语义支持**（向量相似度已达下限）——后者是为了不冤枉
  「确实在讲这件事、只是用词不同」的博文。

**3. 语料里不存在的词被当成「必须命中」，反而误杀真答案。** 「亮片和烫金的裙子怎么洗？」
里的 `亮片` 在这份真实语料里 **df=0**（只有 mock 语料有），它被算作「最生僻」，
于是连真正讲洗护的那条博文都被排除。修法：**df=0 的词不能进「必须命中」集合**。

**4. 但 df=0 反过来是最强的「语料没有」信号——这才是硬负例的解法。**
`山正`/`分辨`/`保养`/`收纳`/`礼仪`/`入坑` 在 615 个片段里 **df=0**。
问题在于：这类提问**在域内却没有答案**，而每条博文都是 lolita 内容，所以向量相似度
照样有 **0.52~0.63**（远高于下限 0.44）——**向量下限在这种提问上彻底失效**。
修法：查询的核心概念（df=0）不存在、且剩下的内容词全是 `lolita`(df=367) 这类
无处不在的词时，**直接返回空**，交给生成层说「资料不足」。
> 反例守住了边界：缺 `亮片`(df=0) 但还有 `烫金`(df=1) 可以锚定 → **不**拒答。

**5. 短文本不构成检索单元。** 681 个片段里 **81 条不足 20 字**（11.9%），它们的
BM25 idf 密度极高（越短越「独特」），于是挤掉了真答案。修法：`CHUNK_MIN_LEN=18`
（默认），短于此长度的博文不入库——**评测集里 11 个正确答案全部是 69~150 字**，
砍掉短贴不会伤到真答案。剔除后 615 个片段，且因为向量缓存在，重建只花了 6 秒。

> **这一轮没有做的事，也值得记下来**：营销/交易贴仍占返回槽位的 20~28%。
> 试算过给它们乘一个降权系数，但 3 道「某条裙子多少钱」的正解本身就是营销贴，
> 降权会伤到它们，而评测头上已经没有空间（MRR 已 0.935）。所以**没做**——
> 这是语料构成问题，不是排序问题，根治要靠换关键词采集（见「已知限制」）。

### 闸门消融：哪几条是真的承重？

到这一步检索层已经堆了 **5 处判定**（向量绝对下限、BM25 相对下限、生僻词锚定、
关键词路的证据门槛、核心概念缺失即拒答）。它们都是我在真实数据上一条条加的，
但**从来没验证过哪一条真的在起作用**——如果某条关掉后指标不动，它就是在白增加复杂度。

```bash
python scripts/ablate_gates.py           # 逐个关掉，跑同一份评测集，比较
python scripts/ablate_gates.py --json
```

实测（32 题评测集，关掉一条、其余不动）：

| 关掉的闸门 | Recall@5 | MRR | 拒答 | 结果变化的题 |
|---|---|---|---|---|
| （baseline） | 1.000 | 0.885 | 1.000 | — |
| **向量绝对下限**（对每一路生效） | **0.917** | **0.862** | **0.750** | 4 |
| **BM25 相对下限**（`MIN_BM25_RATIO`） | 1.000 | 0.885 | 1.000 | **0** |
| 生僻词锚定 | 1.000 | 0.885 | **0.750** | 2 |
| 关键词路证据门槛（≥2 词或全覆盖） | 1.000 | **0.881** | **0.750** | 2 |
| 核心概念缺失即拒答 | 1.000 | 0.885 | **0.750** | 2 |

两条可操作的结论：

1. **`MIN_BM25_RATIO` 在这份评测集上完全不承重**（关掉后 0 题变化）。它原本是用来剪掉
   「只匹配常见词的尾巴」的——但「生僻词锚定」已经把这件事做了。**这是一个候选删除项**，
   不过要先用**真实查询**再验证一遍：32 道题覆盖不到长尾查询，而这条闸门正是为长尾设的。
2. **向量绝对下限是最承重的一条**：关掉它，Recall 从 1.000 掉到 0.917、拒答从 1.000 掉到
   0.750（4 道题翻转）。它同时承担了「防语义噪声」与「判定资料不存在」两件事。

> 工具会列出**具体哪些题翻转了**——只看总分容易被互相抵消的得分掩盖，
> 而真相常常是「某两道题翻车了」。
>
> ⚠️ 消融是直接改运行期对象实现的（settings 字段 + 模块常量），因此**跑完必须恢复**；
> 有测试专门盯着「正常结束」与「中途抛异常」两条路径都要恢复现场——
> 工具改坏全局状态是最难发现的一类 bug，因为它自己「看起来成功了」。

### 切分策略

微博是短文本，**一条博文就是一个检索单元**，切碎只会丢上下文。
只有超过 400 字的整理帖才按句子边界开窗切分，窗口之间保留 50 字重叠。

### 硬约束写进提示词

- 只允许依据【资料】回答，禁止使用资料外的信息；
- 每个结论必须标注 `[编号]`，编号与检索结果严格一一对应（可回溯到原博文链接）；
- 资料不足时**必须**说「资料中没有相关内容」，不许猜。

### 三道兜底，保证「永远跑得通」

| 环节 | 主方案 | 兜底 | 触发条件 |
|---|---|---|---|
| 向量化 | BGE 中文模型 | 字符 n-gram 哈希向量 | 模型缺失/离线/加载失败 |
| 向量库 | chromadb | numpy 内存实现 | chromadb 原生依赖异常 |
| 生成 | LLM（OpenAI 协议） | 原文摘录 + 引用编号 | 未配置 Key / 调用失败 |

降级都会打 `WARNING` 日志，不会静默发生。

## 评测

```bash
python scripts/eval.py                                  # 默认打 eval/qa_mock.jsonl（mock 语料）
python scripts/eval.py --eval-path eval/qa_real.jsonl   # 真实语料要显式指定，否则会报「评测集不匹配」
python scripts/eval.py --eval-path eval/qa_real.jsonl --json   # 机器可读，便于做回归对比
```

指标含义：

| 指标 | 含义 | 为什么关心 |
|---|---|---|
| `Recall@k` | 相关博文被召回的比例 | 没召回就等于没机会答对 |
| `MRR` | 第一条相关结果排名的倒数 | 决定送进 prompt 的上下文质量 |
| `Hit@k` | 至少命中一条的比例 | 粗粒度的可用性判断 |
| 拒答准确率 | 语料确实没有答案时是否承认 | 防硬答/幻觉 |

评测集按 `post_id` 标注，**改动切分策略不需要重新标注**。
调整 `TOP_K`、embedding 模型、RRF 权重后，请重跑一次并对比数值。

> ⚠️ **评测集必须与语料对应**：`eval/qa_mock.jsonl` 标注的是 mock 语料的 `post_id`，
> 只能用于 mock 语料。拿它去打真实语料时，评测会**直接报错**（退出码 2），
> 而不是给出一个会被误读成「检索坏了」的 `Recall@5 = 0.000`。
> 采集真实语料后请另标一份 `eval/qa_real.jsonl`（格式相同）。

> ⚠️ **但「改切分策略不用重标」不等于「换语料来源不用重标」**——实测踩过：
> 同一条博文同时存在导入版（点赞 0）与采集版（点赞 15），`dedupe_posts` 按正文
> 去重并保留点赞更高的那条（更可能是原始出处），于是被标注的那个 `post_id`
> 从语料里消失了，评测静默低估召回。所以换数据来源后要**核对一遍标注 id**；
> 评测会在有标注 id 缺失时打 `WARNING` 说明影响面，别忽略它。

## 生成层评测（答案质量）

`pipeline/eval.py` 只看**检索**（Recall / MRR / 拒答=「检索返回空」）；
这一段看**用户真正读到的那段话**——prompt 里那三条硬约束（只依据资料 / 必须标 `[编号]` /
资料不足要拒答）此前**没有任何东西在验证**。

```bash
python scripts/eval_answer.py            # 真实语料 + 当前生成配置
python scripts/eval_answer.py --limit 5  # 先跑几条看看
python scripts/eval_answer.py --json     # 机器可读（回归脚本用的就是它）
```

四项机器可判定的检查（[src/generator/quality.py](src/generator/quality.py)）：

| 检查 | 判据 | 为什么它重要 |
|---|---|---|
| 引用编号有效 | `[n]` 必须落在 `1..命中条数` 内 | 越界引用等于凭空捏造来源 |
| 有结论就要有引用 | 段落级 | 没有引用就作答说明硬约束没被遵守 |
| 数字/日期不能凭空出现 | ≥2 位数字逐个回查资料 | 价格与日期是这份语料里最要命的事实 |
| 没资料必须拒答 | 检索为空还给出结论 = 硬答 | 防幻觉的最后一道 |

实测（**无 Key，走抽取式兜底**，32 题）：

| 指标 | 值 |
|---|---|
| 引用编号有效 | 1.000（32/32） |
| 引用覆盖率 | 1.000（211/211 句带引用） |
| 无引用就作答 | 0 条 |
| 疑似事实越界 | 0.000（0/32 条，共回查 75 个数字） |
| 无资料时拒答 | 1.000（8/8） |

> ⚠️ **抽取式兜底天然不会编造**，所以「事实越界 = 0」是构造性的结论。
> **配上 `LLM_API_KEY` 后再跑一次，这个数字才有意义**——那才是真正在验证模型的忠实度。
> 这也是当前项目最大的未验证区域。

**它测不了什么**（诚实边界）：把资料的 A 说成 B、把两篇的意思混起来，机器判不出来，
要 LLM-as-judge 或人工抽检；数字提取也只取 **≥2 位**的（单个数字常是模型对资料的正确
归纳，判成编造属于误伤）。

### 先量再改：覆盖率从 0.485 修到 1.000

第一次跑出「引用覆盖率 0.485」，看着像生成层大面积漏标引用。查下来是**指标自己错了**，
而且是三层错叠在一起：

1. 按**句子**判定：抽取式答案是「`[1]` + 整段原文」，一段里好几句话，第 2 句起全被算成无引用；
2. 改成按**空行**切段落仍不对：原文自带空行时，同一条引文被切成两段；
3. 最后把数字算清楚了——剩下的 16 句 = **8 条拒答 × 2 句**：拒答文案本来就没有结论，
   不该进引用覆盖统计。

改完是 1.000（211/211）。**如果不先看数字就去"优化生成层"，等于去修一个本来没坏的东西。**
这个教训和前面几次一样：**指标错了比模型错了更危险，因为它看起来像个结论**。

| 测试污染真实查询日志 | `test_query_log.py::test_tests_can_never_write_into_the_real_project_data_dir` |
| 回归统计把警告文本当成用例数 | `test_regression.py::test_parse_counts_ignores_letters_in_warning_text` |

### 测试绝不许写进真实 `data/`（踩过）

查询日志默认开启，而 `test_ask` / `test_web` 用的是**默认** `Settings`，
于是**跑一次全套测试就往真实查询日志里灌了几十条**——拒答率、延迟分位这些数字
当场被自己的测试污染（症状很好认：日志里出现 `语料外的问题` 这种明显是测试用的查询，
而且 p50 延迟是 0.0 ms）。

`tests/conftest.py` 里加了一个会话级 fixture，从**三层**同时堵：

1. 设环境变量 `DATA_DIR` / `QUERY_LOG_ENABLED`（新构造的 `Settings` 会读到）；
2. 改默认单例的 `data_dir` / `query_log_enabled`；
3. 需要测日志的用例自己构造 `Settings(data_dir=tmp_path)`。

> 只改单例是**不够的**——这一点是实测出来的：测试里显式构造的 `Settings(...)`
> 会重新读配置，照样指向真实目录。

## 回归与 CI

主要资产是「一套能发现问题的评测」，但此前每次都得人工跑 `pytest` + `eval.py`
再人眼看数字——**这个做法已经出过事**：第二轮优化里拒答从 1.000 掉到 0.750，
是靠人肉比对才发现的。所以固化成一条命令：

```bash
python scripts/regression.py              # 跑测试 + 跑评测 + 和基线比，掉指标就退出码 1
python scripts/regression.py --update     # 确认当前结果可接受后写成新基线
python scripts/regression.py --skip-tests # 只跑评测（更快）
```

基线在 [eval/baseline.json](eval/baseline.json)，除指标外还带**参数指纹**
（片段数 / embedding 模型 / 阈值 / 融合方式），并且**检索指标与生成层指标一起比**：

```json
"metrics":        { "recall_at_k": 1.0, "mrr": 0.8847, "hit_rate": 1.0, "refusal_accuracy": 1.0 },
"answer_metrics": { "citation_valid_rate": 1.0, "citation_coverage": 1.0, "unsupported_rate": 0.0,
                    "refusal_rate_without_context": 1.0, "problem_count": 0.0 },
"fingerprint":    { "chunks": 1372, "embedder": "bge:BAAI/bge-small-zh-v1.5", "min_vector_score": 0.44 }
```

指纹不一致时**不判失败**，但会明确提示两组数字不可直接比——这补上了此前
「索引/参数没有版本绑定、无法复现某次评测」的缺口。允许 0.005 的浮点抖动。

> **方向也有讲究**：`unsupported_rate` / `problem_count` 是**越小越好**，比较方向与其余
> 指标相反（`LOWER_IS_BETTER`）。我一开始漏了这一点，还用「现有指标都是越高越好」
> 把自己说服了——那会导致**模型开始编造时回归不报警、它变好反而报回退**。已修正并加测试。

> ⚠️ **真实语料的回归只能在本地跑。** `data/`（语料与索引）不入库，CI 上只有
> `eval/qa_mock.jsonl`，而且 `EMBEDDING_ALLOW_DOWNLOAD=false` 会让它退化成哈希向量
> ——那套数字与线上（BGE + 真实语料）**不可比**。所以
> [.github/workflows/ci.yml](.github/workflows/ci.yml) 覆盖的是「代码没坏」，
> 质量那条线靠本机 `regression.py`。

## 查询日志

每次**真实**检索往 `data/logs/queries.jsonl` 追加一行：查询、来源（web/cli）、命中数、
是否拒答、耗时、分词、**参数指纹**、前 N 条命中摘要。

```bash
python scripts/query_log.py            # 概览：拒答率、延迟分位、高频查询、来源分布
python scripts/query_log.py --refused  # 只看拒答 —— bad case 的候选池
python scripts/query_log.py --popular 20
python scripts/query_log.py --source web --json
```

**为什么必须有**：`eval/qa_real.jsonl` 是读完语料手写的，拿它做优化等于
**自己出题自己答题**——指标涨了也可能只是拟合了那几十道题。线上真实查询是唯一
不受这层影响的证据来源；而 `--refused` 列出的每一条，都是「语料/检索没兜住」的
具体候选，可以直接拿去补语料或补规则。

两条硬约束（实现见 [src/pipeline/query_log.py](src/pipeline/query_log.py)）：

* **写日志失败绝不影响检索**（任何异常都吞掉并打 warning，有测试盯着）；
* **评测与排查脚本不进日志**：`pipeline/eval.py` 与 `explain_retrieval.py` 直接调
  `retriever.search`，天然不经过日志；`ask()` / `retrieve()` 才写，并由调用方声明
  `source`。否则自己的评测会把拒答率这类统计刷满。

### 真实采集打通时修掉的三个真 bug

这两个 bug 都只有在**真实接口 + 真实数据**下才暴露，合成夹具反而把它们写成了「正确行为」。

1. **分页从第 2 页起整页丢失**（`WeiboClient.parse_container`）
   搜索接口第 1 页的博文直接挂在顶层卡片上（`card_type=9`），**第 2 页起改为套一层
   `card_type=11` 的包装卡片**，正文在其 `card_group` 里。旧实现只认顶层 `card_type=9`，
   于是第 2 页起解析结果恒为空、被判成「已到末页」——**采集永远只能拿到第 1 页**。
   症状伪装得很好：8 个关键词各拿到 13 条，看起来「解析正常，只是内容不多」；
   而接口 `cardlistInfo.total` 是 **751**，直接请求 `page=2` 明明返回 10 条。
   改成递归遍历 cards / card_group 后，单关键词 10 页可拿约 106 条。
   > 夹具 `tests/fixtures/weibo_container_page.json` 里原本断言「顶层 card_type=11 的整张卡
   > 都应被忽略」——这条断言本身就是错的，已按真实结构改写。

2. **Cookie 提取挑错了域**（`extract_cookie_from_har`）
   微博登录态分在**两个 Cookie 域**上：`.weibo.com`（PC 站）与 `.weibo.cn`（移动站/API）。
   采集走 `m.weibo.cn`，而 Cookie 按域发送，所以只有 `.weibo.cn` 那一族才用得上。
   旧逻辑只认字面量 `m.weibo.cn`，把 `api.weibo.cn` 当成普通 PC 站，于是按「字段最多」
   选中了 `weibo.com` 那份（10 个字段，看着最全）——但它缺 `SSOLoginState`，
   拿去请求 `/api/config` 得到 `login=false`。而同一份 HAR 里 `api.weibo.cn` 那份
   只有 5 个字段却能登录。现在按「域优先级 > 常见字段命中数 > 字段总数」排序。

3. **「采尽」被当成故障，整轮采集中断**（`WeiboClient._get_json`）
   关键词采尽时，微博返回的不是空页而是
   `{"ok": 0, "msg": "这里还没有内容", "data": {"cards": []}}`。旧实现把所有 `ok != 1`
   都当异常抛出 → **整轮采集中断，后面的关键词一个都采不到**。实测代价很大：
   16 个知识型关键词只采到 5 个，其余 11 个全被跳过（而且是在采了 4 分钟之后）。
   长尾关键词（知识型搜索就是）往往一两页就见底，所以这个假故障几乎废掉了
   「多关键词批量采集」。现在把「`ok=0` 且 `cards` 为空」按空页放行，
   其余 `ok=0`（风控 / 账号异常）仍然报错。
   > 断点续爬在这里救了场：进度是**每页落盘**的，重跑同一条命令就从断点接上。

### 语料扩采：从「排序问题」到「语料问题」的转折

第二轮体检（见下文）得出一条结论：**排序已经没多少空间了，最大短板是语料构成**。
证据是实测 df=0——`山正`/`分辨`/`保养`/`收纳`/`礼仪`/`入坑`/`机洗`/`手洗`
在当时的 615 个片段里**一次都没出现过**：用户最常问的知识型问题，语料里一个字都没有。
这类提问最阴险的地方在于**在域内却没有答案**，而每条博文都是 lolita 内容，
所以向量相似度照样有 0.52~0.63（远高于下限 0.44），**向量下限在这里彻底失效**。

修法不是继续调排序，而是**换关键词采集**：补 16 个知识型关键词
（`lolita 科普`/`lolita 术语`/`lolita 入坑`/`lolita 山正`/`山正 分辨`/`lo裙 洗护`/
`lolita 洗护`/`lo裙 保养`/`lolita 版型`/`lolita 尺码`/`lo裙 搭配`/`lolita 礼仪`/
`lolita 避雷`/`jsk op`/`柄图 科普`/`lolita 手作`），各采 6 页：

| 词 | 扩采前 df | 扩采后 df | | 词 | 扩采前 df | 扩采后 df |
|---|---|---|---|---|---|---|
| 山正 | 0 | **99** | | 入坑 | 0 | **64** |
| 科普 | 0 | **66** | | 避雷 | 0 | **62** |
| 分辨 | 0 | **45** | | 手作 | 0 | **44** |
| 礼仪 | 0 | **30** | | 洗护 | 0 | **29** |
| 机洗 / 手洗 | 0 / 0 | **7 / 6** | | 保养 | 0 | **9** |

语料 **690 → 1478 条**（去重后 1471），检索片段 **615 → 1372**。
同一批提问的效果变化（这是用户唯一能感知的东西）：

| 提问 | 扩采前 top-1 | 扩采后 top-1 |
|---|---|---|
| `JSK 和 OP 有什么区别？` | 一条「三丽鸥合作系列上新」 | 「OP和JSK两款对比图，大家更喜欢哪个型？」 |

> 现在的 MRR 是在 1372 个片段里排出来的，比 615 个片段时的 0.935 更难。

### 环境备注：受限沙箱下的 `WinError 5`（**不是代码问题**）

在受限文件沙箱里跑测试，可能出现**两种**症状，都不是代码缺陷：

| 症状 | 真实原因 |
|---|---|
| `python -m pytest tests/ -q` 报出十几到二十几个 **`ERROR`（在 setup 阶段）**，而不是断言失败 | pytest 要写 `.pytest_cache/` 和 `tmp_path` 用的临时目录，而这些目录上**没有该沙箱会话的授权项**，受限令牌写不进去 |
| 递归列目录时 `Get-ChildItem` 报 `PermissionError: [WinError 5]` | 同上，卡在某个子目录上 |

诊断办法：用 `icacls` 看那个目录的权限项。如果只有 `NT AUTHORITY\SYSTEM`、
`BUILTIN\Administrators`、`OWNER RIGHTS` 和一条 Low 完整性标签，**没有当前用户或
沙箱会话的授权项**，就是这种情况（工作区根目录通常有授权项，所以根目录可写、子目录不可写）。

```powershell
icacls .pytest_cache      # 只列权限项，不修改任何东西
```

解决：把本会话的文件策略切到**完全访问**后重跑即可（`.pytest_cache/` 是纯缓存，
删掉也会自动重建）；或在普通终端里运行。

> 配套的诊断脚本（DSH 的 `diagnose-windows-sandbox-acl`）对这类现象会给出
> `NOT_THIS_CLASS`——它只负责「缺少 `WRITE_DAC`/`WRITE_OWNER`」和「外部应用包授权项」
> 两类问题，**不会**改动上面这种目录。报告落在 `data/acl-recovery/`。
